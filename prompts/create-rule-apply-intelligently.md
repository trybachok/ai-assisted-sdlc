# Промпт для создания Cursor Rule: Apply Intelligently

Правило типа **Apply Intelligently** — это Project Rule, которое агент подключает сам: он читает описание правила (`description`) и решает, относится ли оно к задаче. Хороший промпт на его создание определяет не только содержание правила, но и ситуации, в которых правило должно и не должно подключаться.

Тип подходит, если знания нужны для отдельных видов задач и не привязаны к конкретным файлам. В остальных случаях выберите другой тип:

- указание нужно в любой задаче проекта — [Always Apply](create-rule-always-apply.md);
- указание относится к определённым файлам или папкам — [Apply to Specific Files](create-rule-apply-to-specific-files.md);
- указание нужно редко и только по вашему запросу — [Apply Manually](create-rule-apply-manually.md);
- проекту достаточно простой памятки без настроек — [`AGENTS.md`](create-rule-agents-md.md);
- пожелание личное или общее для всей команды — [User Rule](create-rule-user.md) или [Team Rule](create-rule-team.md).

Требования к формату и актуальные ограничения приведены в [официальной документации Cursor](https://cursor.com/docs/rules). Шаблон правила — [`templates/rule/apply-intelligently.mdc`](../templates/rule/apply-intelligently.mdc), простая инструкция — [`docs/cursor-rules.md`](../docs/cursor-rules.md).

## Требования Cursor

- Правило — файл с расширением `.mdc` в папке `.cursor/rules/` проекта. Имя файла произвольное; файл `.md` в этой папке игнорируется.
- Файл состоит из блока настроек (frontmatter) и текста правила в формате Markdown.
- Для типа Apply Intelligently в frontmatter указывают `description` и `alwaysApply: false`. Поле `globs` не указывают: с ним правило подключается по файлам, а не по описанию.
- Агент видит описание и по нему решает, подключать ли правило. Без описания правило этого типа не сработает, поэтому `description` должен ясно говорить, о чём правило и при каких задачах оно нужно.
- Правило должно быть короче 500 строк, конкретным и посвящённым одной теме. Большое правило делят на несколько.
- На файлы ссылаются упоминанием `@имя-файла` вместо копирования их содержимого. Агент читает такой файл сам, когда он понадобится; в контекст файл автоматически не попадает.
- Не нужно пересказывать руководства по стилю (для этого есть линтер), общеизвестные команды, редкие случаи и код, который уже есть в проекте.

## Структура запроса

```text
Цель:
Какую повторяющуюся ошибку агента исправляет правило или какое поведение закрепляет?

Когда применять:
При каких задачах и запросах агент должен подключать правило?

Когда не применять:
Какие похожие задачи к правилу не относятся?

Требования:
Что агент должен делать и чего не должен? Формулировки конкретные и проверяемые.

Эталонные файлы:
На какие файлы проекта сослаться как на образец вместо копирования их содержимого?

Не входит в правило:
Что остаётся линтеру, другим правилам или документации?

Проверка:
По каким запросам правило должно подключиться, а по каким — нет?
```

## Шаблон промпта

```text
Создай Cursor Rule типа Apply Intelligently.

Цель:


Когда применять:


Когда не применять:


Требования, которые должен соблюдать агент:


Эталонные файлы для ссылок через @:


Не входит в правило:


Позитивные сценарии проверки:


Негативные сценарии проверки:


Процесс создания:
1. Сначала прочитай официальную документацию Cursor Rules:
   https://cursor.com/docs/rules
2. Прочитай шаблон `templates/rule/apply-intelligently.mdc`, существующие
   правила в `.cursor/rules/`, `AGENTS.md` и другие инструкции репозитория.
   Если шаблона в проекте нет, используй формат из официальной документации.
3. Проверь, что правилу действительно нужен тип Apply Intelligently. Если
   указания нужны в каждом чате или относятся к определённым файлам,
   предложи другой тип правила, объясни причину и не создавай правило
   без подтверждения.
4. Перечисли найденные факты, неизвестные детали и необходимые уточнения.
5. Предложи:
   - имя файла в `.cursor/rules/`;
   - значение `description`: одной строкой, о чём правило и когда его
     применять;
   - полный текст правила;
   - сценарии проверки.
6. До подтверждения не изменяй файлы.
7. После подтверждения создай файл `.cursor/rules/<имя>.mdc` по шаблону.
   Frontmatter должен содержать только строки `description`
   и `alwaysApply: false`, без `globs` и комментариев.
8. Проверь расширение `.mdc`, frontmatter, длину правила, существование
   упомянутых файлов, отсутствие секретов, повторов и противоречий
   с другими правилами. Убедись, что `description` отличает позитивные
   сценарии от негативных.
9. Не утверждай, что правило проверено в Cursor, если проверка фактически
   не выполнялась. В таком случае предоставь ручной чек-лист проверки.
```

## Пример

```text
Создай Cursor Rule типа Apply Intelligently.

Цель:
Агент оформляет коммиты и описания pull request по-разному и забывает указать
код задачи Jira. Нужно единое оформление.

Когда применять:
- «Закоммить изменения»;
- «Составь сообщение коммита»;
- «Подготовь описание pull request».

Когда не применять:
- вопросы о том, как работает git;
- изменение кода без коммита.

Требования, которые должен соблюдать агент:
- сообщение коммита начинается с кода задачи Jira, например
  `SCRUM-2 Add booking list page`;
- если код задачи неизвестен, спросить его у пользователя, а не придумывать;
- первая строка сообщения — на английском языке, не длиннее 72 символов;
- в описании pull request есть разделы «Что изменено» и «Как проверено»;
- не выполнять `git push` без явной просьбы.

Эталонные файлы для ссылок через @:
Не нужны.

Не входит в правило:
- стратегия ветвления;
- настройка CI.

Позитивные сценарии проверки:
- на просьбу «Закоммить изменения по задаче SCRUM-15» сообщение коммита
  начинается с `SCRUM-15`;
- на просьбу «Сделай коммит» без кода задачи агент спрашивает код.

Негативные сценарии проверки:
- на вопрос «Чем отличается merge от rebase?» правило не подключается.

Процесс создания:
Сначала изучи официальную документацию, шаблон и существующие правила.
Предложи имя файла, description и текст правила.
До моего подтверждения не изменяй файлы.
```

## Проверка готового правила

1. Убедиться, что файл лежит в `.cursor/rules/` и имеет расширение `.mdc`.
2. Открыть **Customize → Rules** и убедиться, что правило есть в списке, а его тип — **Apply Intelligently**.
3. Убедиться, что `description` заполнен: без него правило этого типа не подключается.
4. В новом чате выполнить позитивные сценарии: агент должен подключить правило сам.
5. В новом чате выполнить негативные сценарии: правило не должно подключаться.
6. Если агент не подключает правило, уточнить `description`: назвать в нём задачи, для которых правило нужно.
7. Сохранить файл в git, чтобы правило получила вся команда.
