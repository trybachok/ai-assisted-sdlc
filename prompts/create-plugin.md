# Промпт для создания Cursor Plugin

Хороший промпт на создание плагина определяет назначение, формат распространения, необходимые компоненты, границы безопасности и способ проверки. Он не должен просить агента слепо копировать весь шаблон.

Перед созданием нужно определить подходящий механизм:

- **Project Skill, Rule или Command** — нужен только одному репозиторию;
- **Personal Skill** — нужен одному пользователю в разных проектах;
- **Cursor Plugin** — нужно распространять skills, rules, agents, commands, hooks, MCP или настройки как единый пакет;
- **Agent Plugin** — нужна переносимость между AI-агентами, а плагин содержит только skills и MCP;
- **Marketplace** — один репозиторий распространяет несколько плагинов.

Требования и актуальные ограничения приведены в официальной документации:

- [Plugins](https://cursor.com/docs/plugins);
- [Plugins reference](https://cursor.com/docs/reference/plugins);
- [Agent Skills](https://cursor.com/docs/skills);
- [Hooks](https://cursor.com/docs/hooks);
- [MCP](https://cursor.com/docs/mcp).

Локальный шаблон Cursor Plugin находится в [`templates/plugin/`](../templates/plugin/), а пояснения по работе с ним — в [`docs/cursor-plugin.md`](../docs/cursor-plugin.md).

## Как выбрать формат

### Cursor Plugin

Используйте, если нужны Cursor-компоненты:

- rules;
- skills;
- agents;
- commands;
- hooks;
- MCP;
- variables.

Минимальная структура:

```text
my-plugin/
└── .cursor-plugin/
    └── plugin.json
```

Обязателен только `.cursor-plugin/plugin.json`, а в нём — поле `name`.

### Agent Plugin

Используйте, если нужны только переносимые skills и MCP:

```text
my-plugin/
├── plugin.json
├── skills/
└── mcp.json
```

Для Agent Plugin обязательны `$schema` и `name`. Шаблон `templates/plugin/` предназначен для Cursor Plugin и не должен копироваться для Agent Plugin без изменения структуры.

## Компоненты Cursor Plugin

| Задача | Компонент | Расположение по умолчанию |
| --- | --- | --- |
| Постоянные инструкции | Rule | `rules/` |
| Повторяемый рабочий процесс | Skill | `skills/<name>/SKILL.md` |
| Изолированная специализированная роль | Agent | `agents/` |
| Явно запускаемое действие | Command | `commands/` |
| Детерминированная реакция на событие | Hook | `hooks/hooks.json` и `scripts/` |
| Подключение внешних инструментов | MCP | `mcp.json` |
| Шаблоны, логотипы и статические файлы | Assets | `assets/` |

Добавляйте только необходимые компоненты. Полный шаблон содержит демонстрационные примеры всех возможностей, а не рекомендуемый состав каждого плагина.

## Основные требования Cursor Plugin

- `name` должен быть уникальным, записан строчными латинскими буквами, цифрами, дефисами или точками и начинаться и заканчиваться буквой или цифрой. Предпочтителен kebab-case.
- `plugin.json`, `hooks.json`, `mcp.json` и `marketplace.json` должны быть строгим JSON без комментариев.
- Все пути должны быть относительными, не содержать `..` и не выходить за корень плагина.
- Стандартные каталоги обнаруживаются автоматически. Явное поле `skills`, `rules`, `agents`, `commands`, `hooks` или `mcpServers` заменяет стандартный поиск соответствующего компонента.
- Skill должен содержать `name` и `description`; имя должно совпадать с родительской папкой.
- Hooks должны содержать только необходимые события. Для security-критичных проверок нужно осознанно выбирать `failClosed`.
- Секреты нельзя хранить в репозитории. Пользовательские значения объявляются через `variables`, а в конфигурации используются плейсхолдеры `${VARIABLE}`.
- Каждый `${VARIABLE}` должен быть объявлен в `variables`; встроенные `${CURSOR_PLUGIN_ROOT}` и `${env:VARIABLE}` не объявляются как plugin variables.
- Удалённые MCP-серверы должны использовать HTTPS, кроме локальных loopback-подключений.
- `README.md` должен описывать назначение, установку, компоненты, настройки и необходимые разрешения.

## Работа с `templates/plugin/`

После копирования шаблона:

1. Заполните `.cursor-plugin/plugin.json`.
2. Оставьте только нужные компоненты и удалите остальные папки.
3. Удалите ненужные явные пути компонентов из `plugin.json`.
4. Удалите `variables`, если плагину не нужны пользовательские значения.
5. Замените демонстрационные skills, rules, agents, commands, hooks и MCP своими.
6. Оставьте в `hooks.json` только реально используемые события.
7. Не используйте фиктивные MCP endpoints и пакеты без проверки их назначения и происхождения.
8. Перепишите `README.md` под создаваемый плагин.
9. Перед публикацией удалите:
   - `*.annotated.jsonc`;
   - `marketplace.example.*`;
   - неиспользуемые demo-компоненты;
   - placeholder-значения и слово `template`.

Файлы `*.annotated.jsonc` предназначены только для чтения разработчиком. Cursor их не использует.

`marketplace.example.json` не является частью одиночного плагина. Для репозитория с несколькими плагинами его нужно адаптировать и разместить в корне репозитория как `.cursor-plugin/marketplace.json`.

## Структура запроса

```text
Цель:
Какую проблему решает плагин?

Пользователи:
Кто и в каких проектах будет использовать плагин?

Формат:
Cursor Plugin или переносимый Agent Plugin?

Компоненты:
Какие rules, skills, agents, commands, hooks и MCP действительно нужны?

Рабочие процессы:
Что должен делать каждый компонент?

Конфигурация:
Какие значения пользователь должен предоставить?

Внешние системы:
Какие API, MCP-серверы, команды или исполняемые файлы используются?

Безопасность:
Какие разрешения, секреты, внешние записи и потенциально опасные действия присутствуют?

Распространение:
Локальная установка, Git-репозиторий, Team Marketplace или публичный Marketplace?

Совместимость:
Какие ОС, shell, Cursor-клиенты и версии должны поддерживаться?

Проверка:
Как проверить каждый компонент и плагин целиком?
```

```text
Процесс создания:
1. Сначала прочитай актуальную официальную документацию:
   - https://cursor.com/docs/plugins
   - https://cursor.com/docs/reference/plugins
   - документацию каждого используемого компонента.
2. Прочитай `docs/cursor-plugin.md`, `templates/plugin/README.md`,
   рабочие и annotated-файлы в `templates/plugin/`, а также инструкции репозитория.
3. Определи, нужен ли Cursor Plugin. Если достаточно project/personal skill,
   rule или command, объясни это и не создавай плагин без подтверждения.
4. Если нужна переносимость между агентами и достаточно skills и MCP,
   предложи Agent Plugin вместо Cursor Plugin.
5. Перечисли подтверждённые требования, предположения и блокирующие вопросы.
6. Предложи до изменения файлов:
   - формат плагина;
   - имя;
   - минимальное дерево файлов;

   - plugin variables;
   - модель безопасности;
   - способ установки и проверки.

   но не изменяй сам шаблон и не копируй ненужные demo-компоненты.
9. Для Cursor Plugin:
   - создай `.cursor-plugin/plugin.json`;
   - оставь только необходимые каталоги;
   - используй стандартное обнаружение компонентов либо проверь каждый явный путь;
   - синхронизируй `${VARIABLE}` с `variables`;
   - оставь только нужные hooks и MCP servers;
   - замени все placeholders;
   - перепиши README.
10. Для Agent Plugin не используй структуру Cursor Plugin:
    создай корневой `plugin.json` с официальной `$schema` и только поддерживаемые
    `skills/` и `mcp.json`.
11. Не добавляй секреты, реальные персональные данные и непроверенные внешние пакеты.
12. Проверь JSON по официальным schemas, относительные пути, имена, frontmatter,
    права исполнения scripts и отсутствие файлов, выходящих за корень плагина.
13. Протестируй плагин локально настолько, насколько позволяет окружение.
14. Не утверждай, что компоненты появились в Cursor или прошли Marketplace review,
    если это фактически не проверялось. Предоставь ручной чек-лист оставшихся проверок.
```

## Пример

```text
Создай плагин для Cursor.

Цель:
Распространять между моими проектами skill, который подготавливает
проверяемый черновик задачи Jira без записи в Jira.

Целевые пользователи и проекты:
Один пользователь, разные репозитории и технологические стеки.

Предпочтительный формат:
Предложи подходящий. Плагин должен устанавливаться в Cursor с user scope.

Компоненты:
- skills: `draft-jira-ticket`;
- rules: не нужны;
- agents: не нужны;
- commands: не нужны;
- hooks: не нужны;
- MCP: не нужен на первом этапе.

Поведение каждого компонента:
Skill принимает GitHub Issue, описание ошибки, запрос функции или заметки,
отделяет факты от предположений и создаёт черновик по отдельному шаблону.

Входные данные и plugin variables:
Переменные не нужны.

Внешние системы и исполняемые команды:
Нет.

Внешние изменения и подтверждения:
Плагин не создаёт и не изменяет задачи Jira.

Требования безопасности:
- не хранить секреты;
- не включать лишние персональные данные;
- не придумывать отсутствующие факты.

Целевые ОС и shell:
macOS, Linux и Windows; scripts отсутствуют.

Способ распространения:
Отдельный публичный Git-репозиторий, сначала локальная установка.

Расположение результата:
Создай новый каталог `plugins/jira-drafting`.

Критерии успешного выполнения:
- валидный `.cursor-plugin/plugin.json`;
- минимальный состав файлов;
- skill обнаруживается из стандартного `skills/`;
- README описывает установку и ограничения;
- в репозитории нет секретов, demo hooks и demo MCP.

Позитивные сценарии проверки:
- явный запуск `/draft-jira-ticket`;
- автоматический выбор для запроса «Оформи это как черновик Jira».

Негативные и ошибочные сценарии:
- skill не выбирается для вопроса «Что такое Jira?»;
- при недостатке данных задаёт уточняющие вопросы;
- при отсутствии Jira tools всё равно создаёт локальный черновик.

Процесс создания:
Сначала изучи официальную документацию и `templates/plugin/`.
Предложи формат, имя, минимальное дерево файлов и проверки.
До моего подтверждения не изменяй файлы.
```

## Проверка готового плагина

1. Проверить строгий JSON и официальные schemas для manifest, marketplace и MCP.
2. Убедиться, что все пути относительные, существуют и остаются внутри корня плагина.
3. Убедиться, что имена skills совпадают с папками, а frontmatter компонентов валиден.
4. Найти оставшиеся placeholders, demo endpoints, demo packages и секреты.
5. Проверить, что каждый `${VARIABLE}` объявлен, а неиспользуемые variables удалены.
6. Проверить права исполнения и ошибочные сценарии scripts.
7. Проверить hooks по одному событию, включая поведение при ошибке и `failClosed`.
8. Проверить MCP с минимальными правами и изучить исходники внешних пакетов.
9. Скопировать плагин в `~/.cursor/plugins/local/<plugin-name>`.
10. Перезапустить Cursor или выполнить `Developer: Reload Window`.
11. Проверить компоненты в **Customize**, Hooks output и MCP logs.
12. Перед публикацией переписать README и удалить annotated/example/demo-файлы.
13. Для multi-plugin репозитория проверить корневой `.cursor-plugin/marketplace.json`
    и уникальность имён плагинов.
14. Не считать локальную проверку эквивалентом Marketplace review.
