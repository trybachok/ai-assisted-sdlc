# Промпт для создания Cursor Rule: Apply to Specific Files

Правило типа **Apply to Specific Files** — это Project Rule, которое Cursor подключает сам, когда агент работает с файлом, подходящим под glob-шаблон из поля `globs`. Хороший промпт на его создание точно называет файлы, к которым относится правило, и примеры путей, которые должны и не должны под него попадать.

Тип подходит, если требования привязаны к определённым файлам или папкам: компонентам, миграциям, тестам, документации. В остальных случаях выберите другой тип:

- указание нужно в любой задаче проекта — [Always Apply](create-rule-always-apply.md);
- указание нужно для отдельных видов задач и не привязано к файлам — [Apply Intelligently](create-rule-apply-intelligently.md);
- указание нужно редко и только по вашему запросу — [Apply Manually](create-rule-apply-manually.md);
- проекту достаточно простой памятки без настроек — [`AGENTS.md`](create-rule-agents-md.md);
- пожелание личное или общее для всей команды — [User Rule](create-rule-user.md) или [Team Rule](create-rule-team.md).

Требования к формату и актуальные ограничения приведены в [официальной документации Cursor](https://cursor.com/docs/rules). Шаблон правила — [`templates/rule/apply-to-specific-files.mdc`](../templates/rule/apply-to-specific-files.mdc), простая инструкция — [`docs/cursor-rules.md`](../docs/cursor-rules.md).

## Требования Cursor

- Правило — файл с расширением `.mdc` в папке `.cursor/rules/` проекта. Имя файла произвольное; файл `.md` в этой папке игнорируется.
- Файл состоит из блока настроек (frontmatter) и текста правила в формате Markdown.
- Для типа Apply to Specific Files в frontmatter указывают `globs` и `alwaysApply: false`. Поле `description` для подключения не используется.
- Правило подключается автоматически, когда в контексте есть файл, подходящий под шаблон. Если правило не срабатывает, первым делом проверяют, подходит ли шаблон к нужным файлам.
- Несколько шаблонов перечисляют в одной строке через запятую.
- Правило должно быть короче 500 строк, конкретным и посвящённым одной теме. Большое правило делят на несколько.
- На файлы ссылаются упоминанием `@имя-файла` вместо копирования их содержимого. Агент читает такой файл сам, когда он понадобится; в контекст файл автоматически не попадает.
- Не нужно пересказывать руководства по стилю (для этого есть линтер), общеизвестные команды, редкие случаи и код, который уже есть в проекте.

Примеры glob-шаблонов:

| Шаблон | Какие файлы подходят |
| --- | --- |
| `*.ts` | Все файлы `.ts` в корне проекта |
| `**/*.ts` | Все файлы `.ts` в любой папке |
| `src/**` | Все файлы внутри `src/` |
| `src/**/*.tsx` | Все файлы `.tsx` внутри `src/` |
| `docs/**/*.md, docs/**/*.mdx` | Файлы `.md` и `.mdx` внутри `docs/` |
| `tailwind.config.*` | Файл `tailwind.config` с любым расширением |

## Структура запроса

```text
Цель:
Какую повторяющуюся ошибку агента исправляет правило или какое поведение закрепляет?

Файлы:
К каким файлам и папкам относится правило?
Какие пути должны подходить под правило, а какие — нет?

Требования:
Что агент должен делать и чего не должен? Формулировки конкретные и проверяемые.

Эталонные файлы:
На какие файлы проекта сослаться как на образец вместо копирования их содержимого?

Не входит в правило:
Что остаётся линтеру, другим правилам или документации?

Проверка:
При работе с какими файлами правило должно подключиться, а с какими — нет?
```

## Шаблон промпта

```text
Создай Cursor Rule типа Apply to Specific Files.

Цель:


Файлы, к которым относится правило:


Пути, которые должны подходить:


Пути, которые не должны подходить:


Требования, которые должен соблюдать агент:


Эталонные файлы для ссылок через @:


Не входит в правило:


Сценарии проверки:


Процесс создания:
1. Сначала прочитай официальную документацию Cursor Rules:
   https://cursor.com/docs/rules
2. Прочитай шаблон `templates/rule/apply-to-specific-files.mdc`, существующие
   правила в `.cursor/rules/`, `AGENTS.md` и другие инструкции репозитория.
   Если шаблона в проекте нет, используй формат из официальной документации.
3. Проверь, что правилу действительно нужен тип Apply to Specific Files. Если
   указания не привязаны к файлам, предложи другой тип правила, объясни
   причину и не создавай правило без подтверждения.
4. Перечисли найденные факты, неизвестные детали и необходимые уточнения.
5. Предложи:
   - имя файла в `.cursor/rules/`;
   - значение `globs`;
   - список существующих файлов проекта, которые подходят под `globs`;
   - полный текст правила;
   - сценарии проверки.
6. До подтверждения не изменяй файлы.
7. После подтверждения создай файл `.cursor/rules/<имя>.mdc` по шаблону.
   Frontmatter должен содержать только строки `globs`
   и `alwaysApply: false`, без комментариев. Несколько шаблонов запиши
   в одну строку через запятую.
8. Проверь расширение `.mdc`, frontmatter, длину правила, существование
   упомянутых файлов, отсутствие секретов, повторов и противоречий
   с другими правилами. Убедись, что под `globs` попадают все нужные пути
   и не попадают лишние.
9. Не утверждай, что правило проверено в Cursor, если проверка фактически
   не выполнялась. В таком случае предоставь ручной чек-лист проверки.
```

## Пример

```text
Создай Cursor Rule типа Apply to Specific Files.

Цель:
Агент пишет миграции без отката и меняет типы столбцов на месте. Нужны единые
требования к миграциям базы данных.

Файлы, к которым относится правило:
Все миграции Laravel в папке `database/migrations/`.

Пути, которые должны подходить:
- `database/migrations/2026_01_15_000000_create_bookings_table.php`.

Пути, которые не должны подходить:
- `database/seeders/DatabaseSeeder.php`;
- `app/Models/Booking.php`.

Требования, которые должен соблюдать агент:
- у каждой миграции есть рабочие методы `up` и `down`;
- тип столбца не меняется на месте: добавить новый столбец, перенести данные,
  старый столбец удалить отдельной миграцией;
- уже применённые миграции не редактируются: для изменений создаётся новая;
- индексы и внешние ключи получают явные имена.

Эталонные файлы для ссылок через @:
`database/migrations/2026_01_15_000000_create_bookings_table.php` — образец
структуры миграции.

Не входит в правило:
- сидеры и фабрики;
- оформление кода: его проверяет Laravel Pint.

Сценарии проверки:
- на просьбу «Добавь столбец status в таблицу bookings» агент создаёт новую
  миграцию с методом `down`;
- при работе только с моделью `app/Models/Booking.php` правило
  не подключается.

Процесс создания:
Сначала изучи официальную документацию, шаблон и существующие правила.
Предложи имя файла, globs, список подходящих файлов и текст правила.
До моего подтверждения не изменяй файлы.
```

## Проверка готового правила

1. Убедиться, что файл лежит в `.cursor/rules/` и имеет расширение `.mdc`.
2. Открыть **Customize → Rules** и убедиться, что правило есть в списке, а его тип — **Apply to Specific Files**.
3. Сверить `globs` с реальными путями проекта: подходят все нужные файлы и не подходят лишние.
4. В новом чате дать задачу по файлу, который подходит под шаблон: агент должен соблюдать правило.
5. В новом чате дать задачу по файлу, который не подходит под шаблон: правило не должно подключаться.
6. Если правило не срабатывает, проверить шаблон: чаще всего он не соответствует путям файлов.
7. Сохранить файл в git, чтобы правило получила вся команда.
