# Промпт для создания Cursor Skill

Хороший промпт на создание skill описывает не только желаемое поведение, но и условия его активации, границы ответственности и способ проверки.

Перед созданием нужно убедиться, что выбран правильный механизм:

- **Skill** — повторяемая процедура, чек-лист или специализированный рабочий процесс;
- **Rule / `AGENTS.md`** — правило, которое должно действовать постоянно;
- **Prompt** — разовая или явно запускаемая инструкция без отдельного рабочего процесса;
- **Script или tool** — операция, результат которой должен быть детерминированным.

Требования к формату и актуальные ограничения приведены в [официальной документации Cursor](https://cursor.com/docs/skills).

## Требования Cursor

- Каждый skill находится в отдельной папке с файлом `SKILL.md`.
- `name` обязателен, содержит только строчные латинские буквы, цифры и дефисы, совпадает с названием родительской папки и не превышает 64 символа.
- `description` обязателен, не превышает 1024 символа и объясняет, что делает skill и когда его использовать.
- Основной текст `SKILL.md` должен оставаться сфокусированным и занимать примерно до 5000 токенов.
- Большие справочные материалы следует выносить в `references/`, шаблоны — в `assets/`, исполняемые операции — в `scripts/`.
- `paths` следует добавлять только для ограничения skill определёнными файлами.
- `disable-model-invocation: true` следует использовать, если skill разрешено запускать только явно.
- В skill нельзя хранить токены, пароли и другие секреты.

## Структура запроса

```text
Цель:
Какой повторяемый результат должен создавать skill?

Когда использовать:
Какие пользовательские запросы должны активировать skill?

Когда не использовать:
Какие похожие запросы не относятся к skill?

Входные данные:
Что обязательно и что необязательно предоставляет пользователь?

Результат:
Что именно должен вернуть или создать skill?

Порядок работы:
Какие шаги необходимо выполнить?

Инструменты:
Какие файлы, MCP, API, команды или скрипты могут потребоваться?

Внешние изменения:
Создаёт ли skill задачи, комментарии, PR или другие внешние ресурсы?
Когда требуется подтверждение пользователя?

Область действия:
Должен ли skill работать во всех проектах или только с определёнными путями?

Способ запуска:
Автоматический выбор моделью или только явный вызов?

Дополнительные материалы:
Какие справочники, шаблоны, примеры или скрипты нужно вынести из SKILL.md?

Проверка:
Как доказать, что skill корректно активируется и выполняет задачу?
```

## Шаблон промпта

```text
Создай Cursor Skill.

Цель:


Когда использовать:


Когда не использовать:


Обязательные входные данные:


Необязательные входные данные:


Ожидаемый результат:


Порядок работы:


Необходимые инструменты:


Внешние изменения и подтверждения:


Область действия и paths:


Способ запуска:
Автоматический / только явный.


Дополнительные references, assets или scripts:


Позитивные сценарии активации:


Негативные сценарии активации:


Критерии успешного выполнения:


Процесс создания:
1. Сначала прочитай официальную документацию Cursor Skills:
   https://cursor.com/docs/skills
2. Прочитай `templates/skill/SKILL.template.md`, существующие skills и инструкции репозитория.
3. Проверь, что задача действительно подходит для skill. Если лучше использовать Rule, Prompt, script или tool, объясни причину и не создавай skill без подтверждения.
4. Перечисли найденные факты, неизвестные детали и необходимые уточнения.
5. Предложи:
   - имя skill;
   - значение `description`;
   - дерево файлов;
   - способ запуска;
   - сценарии проверки.
6. До подтверждения не изменяй файлы.
7. После подтверждения создай skill по шаблону, добавляя только необходимые директории и файлы.
8. Проверь ограничения `name`, `description`, размер SKILL.md, относительные пути и отсутствие секретов.
9. Не утверждай, что skill проверен в Cursor, если запуск фактически не выполнялся. В таком случае предоставь команды и ручной чек-лист проверки.
```

## Пример

```text
Создай Cursor Skill.

Цель:
Подготавливать проверяемый черновик задачи Jira из GitHub Issue, сообщения об ошибке, запроса функции или заметок.

Когда использовать:
- «Подготовь черновик задачи Jira»;
- «Оформи это как Jira ticket»;
- «Структурируй требования для Jira».

Когда не использовать:
- пользователь просит только объяснить возможности Jira;
- пользователь просит изменить существующую задачу;
- пользователь просит немедленно создать задачу в Jira.

Обязательные входные данные:
- описание проблемы или ссылка на источник.

Необязательные входные данные:
- Jira project;
- предполагаемый тип задачи;
- ограничения;
- критерии приёмки.

Ожидаемый результат:
Черновик с заголовком, проблемой, текущим и ожидаемым поведением, критериями приёмки, ограничениями, источником, предположениями и нерешёнными вопросами.

Порядок работы:
1. Прочитать источник.
2. Отделить факты от предположений.
3. Определить недостающие данные.
4. Задать только блокирующие вопросы.
5. При наличии read-only Jira tools найти возможные дубликаты.
6. Подготовить черновик по отдельному шаблону.
7. Проверить, что критерии приёмки наблюдаемы и тестируемы.

Необходимые инструменты:
- доступ к источнику;
- необязательный read-only Jira MCP.

Внешние изменения и подтверждения:
Skill не создаёт и не изменяет задачи Jira.

Область действия и paths:
Персональный skill для всех проектов, `paths` не нужны.

Способ запуска:
Автоматический выбор моделью и явный вызов `/draft-jira-ticket`.

Дополнительные references, assets или scripts:
- `references/ticket-template.md`;
- scripts не нужны.

Позитивные сценарии активации:
- «Подготовь Jira ticket по этому GitHub Issue»;
- «Оформи описание ошибки как черновик Jira».

Негативные сценарии активации:
- «Что такое Jira?»;
- «Покажи мои задачи Jira».

Критерии успешного выполнения:
- skill не выполняет внешних записей;
- не придумывает отсутствующие сведения;
- помечает неподтверждённые предположения;
- выдаёт все обязательные разделы черновика.

Процесс создания:
Сначала проверь официальную документацию и существующий шаблон.
Предложи имя, description, дерево файлов и сценарии проверки.
До моего подтверждения не изменяй файлы.
```

## Проверка готового skill

1. Открыть `Customize → Skills` или выполнить `/skills` и убедиться, что Cursor обнаружил skill без предупреждений.
2. Запустить skill явно через `/skill-name`.
3. Проверить несколько подходящих запросов, для которых skill должен выбираться автоматически.
4. Проверить похожие неподходящие запросы, для которых skill не должен активироваться.
5. Проверить поведение при отсутствии обязательных данных и необходимых инструментов.
6. Если skill содержит scripts, проверить успешный сценарий, ошибки и граничные случаи.
7. Убедиться, что внешние изменения требуют предусмотренного подтверждения.
