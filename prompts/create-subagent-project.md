# Промпт для создания Cursor Subagent: Project subagent

**Project subagent** — субагент одного проекта: файл в папке `.cursor/agents/`, который хранится вместе с проектом и доступен всем, кто с ним работает. Основной агент передаёт такому субагенту задачу сам, по его описанию (`description`), или по вашему явному вызову. Хороший промпт на его создание определяет зону ответственности субагента, порядок его работы и ситуации, в которых задачу нужно и не нужно ему передавать.

Тип подходит, если помощник нужен в одном проекте и опирается на его команды, файлы и соглашения. В остальных случаях выберите другой тип:

- помощник нужен лично вам во всех проектах — [User subagent](create-subagent-user.md);
- помощник должен только проверять и ничего не изменять — [Read-only subagent](create-subagent-readonly.md);
- работа долгая, и основной агент не должен её ждать — [Background subagent](create-subagent-background.md);
- задачу нужно выполнить в облаке, не занимая ваш компьютер, — [Cloud subagent](create-subagent-cloud.md);
- задача простая и выполняется за один шаг — вместо субагента создайте [Cursor Skill](create-skill.md).

Требования к формату и актуальные ограничения приведены в [официальной документации Cursor](https://cursor.com/docs/subagents). Шаблон субагента — [`templates/subagent/project-subagent.md`](../templates/subagent/project-subagent.md), простая инструкция — [`docs/cursor-subagents.md`](../docs/cursor-subagents.md).

## Требования Cursor

- Субагент — файл Markdown в папке `.cursor/agents/` проекта. Он действует только в этом проекте.
- Файл состоит из блока настроек (YAML frontmatter) и текста задания под ним.
- В блоке настроек указывают `name` — имя из строчных латинских букв и дефисов; по умолчанию оно берётся из имени файла — и `description`. Необязательные поля: `model` (по умолчанию `inherit`), `readonly` и `is_background` (по умолчанию `false`).
- Основной агент читает `description` и по нему решает, передавать ли задачу. Описание должно быть конкретным; слова «используй проактивно» или «всегда используй для…» поощряют автоматическую передачу.
- Субагент начинает работу с чистым контекстом и не видит историю переписки: всё необходимое он получает из своего задания и из запроса основного агента.
- У субагента должна быть одна чёткая зона ответственности, а задание должно быть коротким и конкретным. Для простой задачи, которая выполняется за один шаг, вместо субагента используют skill.
- При совпадении имён Project subagent главнее User subagent, а папка `.cursor/` главнее `.claude/` и `.codex/`.
- Папку `.cursor/agents/` сохраняют в git, чтобы субагента получила вся команда.

## Структура запроса

```text
Цель:
Какую работу основной агент должен передавать субагенту и зачем?

Когда вызывать:
При каких задачах и запросах агент должен передавать работу субагенту?

Когда не вызывать:
Какие похожие задачи субагенту не передаются?

Порядок работы:
Что субагент делает по шагам? Какие команды и файлы проекта использует?

Отчёт:
Что субагент должен вернуть основному агенту?

Настройки:
Нужна ли другая модель? Достаточно ли прав только на чтение?
Ждать результат или работать в фоне?

Не входит в задачу субагента:
Что остаётся основному агенту, другим субагентам, правилам или skill?

Проверка:
По каким запросам субагент должен вызываться, а по каким — нет?
```

## Шаблон промпта

```text
Создай Cursor Subagent типа Project subagent.

Цель:


Когда вызывать субагента:


Когда не вызывать:


Порядок работы субагента:


Что субагент должен вернуть:


Настройки:
Модель: та же, что у основного агента / другая (какая).
Права: обычные / только чтение.
Режим: Foreground (агент ждёт результат) / Background (работа в фоне).


Не входит в задачу субагента:


Позитивные сценарии проверки:


Негативные сценарии проверки:


Процесс создания:
1. Сначала прочитай официальную документацию Cursor Subagents:
   https://cursor.com/docs/subagents
2. Прочитай шаблон `templates/subagent/project-subagent.md`, существующих
   субагентов в `.cursor/agents/`, `AGENTS.md`, правила и другие инструкции
   репозитория. Если шаблона в проекте нет, используй формат из официальной
   документации.
3. Проверь, что задаче действительно нужен Project subagent. Если задача
   простая и выполняется за один шаг, предложи skill. Если помощник нужен
   во всех проектах пользователя, предложи User subagent. Объясни причину
   и не создавай субагента без подтверждения.
4. Перечисли найденные факты, неизвестные детали и необходимые уточнения.
   Команды, пути и инструменты бери из репозитория, а не придумывай.
5. Предложи:
   - имя субагента: строчные латинские буквы и дефисы;
   - значение `description`: одной строкой, что делает субагент и когда
     передавать ему задачу;
   - значения `model`, `readonly` и `is_background`;
   - полный текст задания;
   - сценарии проверки.
6. До подтверждения не изменяй файлы.
7. После подтверждения создай файл `.cursor/agents/<имя>.md` по шаблону.
   Значение `name` должно совпадать с именем файла. Каждую настройку запиши
   в одну строку, без кавычек и без пояснений после значения; в `description`
   не используй двоеточия и символ `#`.
8. Проверь расположение и расширение файла, блок настроек, отсутствие
   субагента с таким же именем, существование упомянутых команд и путей,
   отсутствие секретов и противоречий с правилами проекта. Убедись, что
   `description` отличает позитивные сценарии от негативных, а задание
   понятно без истории переписки.
9. Не утверждай, что субагент проверен в Cursor, если проверка фактически
   не выполнялась. В таком случае предоставь ручной чек-лист проверки.
```

## Пример

```text
Создай Cursor Subagent типа Project subagent.

Цель:
Агент иногда называет задачу выполненной, хотя тесты не проходят или часть
требований не реализована. Нужен независимый проверяющий
для Laravel-приложения бронирований.

Когда вызывать субагента:
- после того как задача названа выполненной;
- «Проверь, что задача действительно сделана»;
- перед коммитом изменений.

Когда не вызывать:
- вопросы о том, как устроен код;
- задачи, в которых код не менялся.

Порядок работы субагента:
1. Определить, какая работа названа выполненной, и найти изменённые файлы.
2. Сверить изменения с критериями приёмки из задачи.
3. Запустить релевантные тесты PHPUnit и Laravel Pint.
4. Проверить граничные случаи: пустой список, отсутствие прав доступа.

Что субагент должен вернуть:
- что проверено и работает;
- что названо выполненным, но не сделано или не работает;
- что именно нужно исправить.

Настройки:
Модель — та же, что у основного агента.
Права обычные: субагент запускает тесты.
Режим Foreground: основной агент ждёт результат проверки.

Не входит в задачу субагента:
- исправление найденных проблем: их исправляет основной агент;
- проверка оформления коммитов.

Позитивные сценарии проверки:
- после слов «Готово, страница со списком бронирований добавлена» основной
  агент сам передаёт проверку субагенту;
- на запрос «/verifier проверь экспорт бронирований» субагент запускает
  тесты и перечисляет, что не работает.

Негативные сценарии проверки:
- на вопрос «Как устроена авторизация?» субагент не вызывается.

Процесс создания:
Сначала изучи официальную документацию, шаблон и репозиторий.
Предложи имя, description, настройки и текст задания.
До моего подтверждения не изменяй файлы.
```

## Проверка готового субагента

1. Убедиться, что файл лежит в `.cursor/agents/`, имеет расширение `.md`, а его имя совпадает со значением `name`.
2. Открыть **Customize → Subagents** и убедиться, что субагент есть в списке.
3. В новом чате вызвать субагента явно, например `/verifier проверь, что вход в систему работает`: в чате должна появиться карточка задачи субагента.
4. Выполнить позитивные сценарии: основной агент должен передать задачу субагенту сам.
5. Выполнить негативные сценарии: субагент не должен вызываться.
6. Если агент не передаёт задачу сам, уточнить `description`: назвать в нём задачи, для которых нужен субагент.
7. Сохранить файл в git, чтобы субагента получила вся команда.
